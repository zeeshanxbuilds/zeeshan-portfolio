# Zeeshan Utils project entry with copyable run command and `/utils` script rewrite (v2)

This pass checks the fixes for the v1 review. The project schema now has three optional fields, `category`, `command` and `commandInstruction`, so the detail page no longer hardcodes either the "Mobile Project" pill or the Windows/admin lead-in. The two Flutter pages render the same as before, because `category` falls back to "Mobile Project" and Quick Start only appears when `command` is set. The data entry, logo, `CodeBlock`, `vercel.json` additions and the `featured: false` decision haven't changed since v1. Nothing in the diff itself blocks shipping. The remaining blockers are deployment prerequisites the agent can't resolve under the user's rules.

Watch for: `/utils` will still 404 until the user moves the root `winutil.ps1` into `public/` (confirmed: `public/winutil.ps1` is absent). The command's `zeeshanxbuilds.tech` domain is still unverified against `siteConfig.url` (`https://zeeshanxbuilds.vercel.app`) (confirmed mismatch). Lint and build have still not run (confirmed).

**Verdict**: APPROVED. The code change is ready, but shipping depends on the three user actions in the Issues list.

## High-level view

The v1 template issues are fixed by moving the wording into project data. Zeeshan Utils sets `category: "Windows Utility"` and its own PowerShell instruction, and the generic template no longer assumes either. The one leftover is the default: a project that leaves out `category` is still labeled mobile.

The script delivery path is unchanged from v1. The rewrite target is still missing from `public/`, and the command still depends on a domain that the repo doesn't tie to this deployment. Both are user actions, and so is running `npm ci`/lint/build where the registry is reachable.

### Asymmetric defaults for `category` and `commandInstruction`

```tsx
{project.category ?? "Mobile Project"}
...
{project.command && (
  <section>
    {project.commandInstruction && <p>{project.commandInstruction}</p>}
    <CodeBlock code={project.command} />
  </section>
)}
```

`commandInstruction` defaults to nothing, so a future project with a `command` gets no admin/PowerShell framing. `category` defaults to a specific claim ("Mobile Project"), which is wrong for anything that isn't a Flutter app (confirmed, line 47). The site-wide copy that still describes the work as mobile-only is unchanged and was raised in v1: the `/projects` intro, its metadata/OG description, and the `CollectionPage` JSON-LD description. Zeeshan Utils appears in that grid even though it isn't featured.

### `/utils` delivery still gated on user actions

`public/winutil.ps1` still doesn't exist (confirmed via `Test-Path`, without opening the file). `Invoke-RestMethod` throws on the 404, so the command fails closed and nothing executes. The `Content-Type: text/plain` header likely matters for more than hygiene: without it Vercel would probably serve `.ps1` as a binary type, and `irm` might not hand `iex` a plain string. Whether Vercel applies the custom headers to the rewritten static response can only be checked against a deployed response, which is part of issue 3.

Not tested: lint, typecheck, build output, sitemap contents, the Copy button in a browser, `/utils` response headers on Vercel, or whether `zeeshanxbuilds.tech` resolves to this deployment.
