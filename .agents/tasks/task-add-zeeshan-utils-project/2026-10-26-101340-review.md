# Zeeshan Utils project entry with copyable run command and `/utils` script rewrite (v1)

The change adds a third portfolio project, Zeeshan Utils, a Windows utility forked from ChrisTitusTech/winutil. It also wires up `/utils` so that `irm https://zeeshanxbuilds.tech/utils | iex` fetches the PowerShell script from this Vercel deployment. The project schema gets an optional `command` field. When `command` is set, the detail page renders a "Quick Start" section through a new client-side `CodeBlock` with a Copy button. `vercel.json` gains a rewrite from `/utils` to `/winutil.ps1` and plain-text/no-cache headers. The cleanup in `constants/projects.ts` only removes the unused `siteConfig` import, because the quoted `githubUrl` values and hyphenated slugs were already on `main`.

Watch for: the rewrite target doesn't exist in the build output. `public/winutil.ps1` is missing and the script sits untracked at the repo root, so `/utils` will 404 in production (confirmed). The advertised command uses `zeeshanxbuilds.tech`, but the site's canonical URL is `zeeshanxbuilds.vercel.app`, and nothing in the repo shows that the `.tech` domain is attached to this project (confirmed mismatch, attachment unverified). Lint and build were never run.

**Verdict**: NEEDS_CHANGES

## High-level view

The project is added purely as data, and Quick Start appears only on projects that set the optional `command` field. The project is deliberately left unfeatured, because a third card in the two-column homepage grid would sit alone on its row. `generateStaticParams` and `sitemap.ts` both read from `projects`, so the new page is generated and listed without extra wiring. No route under `app/` conflicts with `/utils`.

The script delivery path is the broken part. Vercel can only serve `/winutil.ps1` if the file is in `out/`, which means it has to be in `public/`. It's currently at the repo root, so `/utils` resolves to nothing. The command shown to visitors also depends on `zeeshanxbuilds.tech` routing to this deployment, which the repo doesn't establish.

Adding this project also turns this deployment and the `.tech` domain into a code-execution path: whatever `/utils` returns runs as administrator on visitors' machines.

The detail page template still hardcodes Flutter-era framing, so the new project page shows a "Mobile Project" pill above a Windows PowerShell tool.

### `/utils` rewrite points at a file the build doesn't contain

Because of `output: "export"`, Vercel serves only what lands in `out/`, and static files reach `out/` only from `public/`. A listing of `public/` shows no `winutil.ps1`. `git status` shows `?? winutil.ps1` at the repo root, a location that is never copied into the export. The rewrite's destination will 404 (confirmed). For a visitor, `Invoke-RestMethod` throws on the 404 status, so `iex` never runs anything. That fails closed, but the advertised command simply doesn't work. The user's instructions describe the script as already being at `public/winutil.ps1`, so the misplacement probably happened when the file was copied in, not in this change. The root copy is also not ignored by `.gitignore`, so a broad `git add` would commit it at the wrong path.

```
visitor ──irm──▶ zeeshanxbuilds.tech/utils ──?──▶ Vercel project
                                                    │ rewrite
                                                    ▼
                                             /winutil.ps1  ← not in out/ (missing from public/)
```

### Trust boundary behind `irm | iex`

`/utils` is now a remote-code-execution endpoint by design: visitors pipe its response into `iex` from an elevated shell. Two things in this change carry that trust. The first is the domain. The command hardcodes `zeeshanxbuilds.tech`, while every canonical URL, sitemap entry and JSON-LD URL in the site uses `zeeshanxbuilds.vercel.app` (confirmed in `constants/site.ts`). The repo has no evidence that `.tech` routes to this project. If it isn't attached, the command fails. If the domain ever lapses or is pointed elsewhere, whoever controls it controls what admin shells execute. The second is the deployment path: anyone who can push to the branch Vercel builds from, or who has access to the Vercel project, can change the script. The script has no integrity check, which is inherent to the `irm | iex` pattern that upstream WinUtil also uses. That puts the protection of the repo and the domain renewal on the critical path.

### Quick Start section and `CodeBlock`

The `command` field is rendered only on the detail page, between the GitHub button and the Key Features grid. The same string also appears verbatim as a feature bullet, which the task required. The duplication is intentional but visible on the page. The lead-in sentence "Open PowerShell as administrator and run:" is hardcoded in the shared template, not taken from the project, so the template now assumes every `command` is an elevated PowerShell one (confirmed, `app/projects/[slug]/page.tsx`).

When the Clipboard API fails, `CodeBlock` gives no feedback and the label stays "Copy". The command is still selectable in the `<pre>`, so this isn't blocking.

### Category framing on the new page

The detail template's "Mobile Project" pill was unchanged by this diff, but it now renders above a PowerShell/WPF utility (confirmed, line 47). The `/projects` intro and its metadata description still describe the list as "Mobile applications I've built with Flutter and Firebase, from a real-time bookstore to cloud-synced notes", and the README's project table lists only the two Flutter apps. The pill is the most visible mismatch. The rest is copy that will drift further as non-mobile projects are added.

### Verification gap

No lint, typecheck or build ran, because `npm ci` failed with `ENOTFOUND` / `ENOTCACHED`, and the repo has no automated tests. The two outputs the task explicitly asked to confirm, `out/winutil.ps1` and `out/projects/zeeshan-utils`, are unverified, and the first one is known to be absent.

Not tested: build output, lint, the Copy button in a browser, the `/utils` response headers on Vercel, or whether `zeeshanxbuilds.tech` resolves to this deployment.
